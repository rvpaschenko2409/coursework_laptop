# Веб-модуль: регистрация и доступ к проектам

Этап курсовой работы, вариант 27. Дата: 30.10.2026.

## Реализованные возможности

FastAPI обслуживает русскоязычные страницы Jinja2. Bootstrap 5.3.3 и дополнительные стили находятся в проекте; внешние CDN и JavaScript для этого этапа не нужны. Сервер запускается на 127.0.0.1:8000. Через браузер можно зарегистрироваться, войти, выйти, создать проект, открыть доступный проект и просмотреть его таблицу решений.

Новый проект содержит пять критериев исходного варианта: цена, прогнозная производительность, масса, автономность и гарантия. Альтернативы в новом проекте пока отсутствуют. Аналитик может предоставить зарегистрированному активному пользователю роль аналитика, эксперта или ЛПР в конкретном проекте. Создатель нового проекта становится его аналитиком.

| Действие | Аналитик проекта | Эксперт проекта | ЛПР проекта | Посторонний пользователь |
|---|---|---|---|---|
| Просмотр проекта и оценок | Да | Да | Да | Нет |
| Просмотр списка участников и email | Да | Нет | Нет | Нет |
| Назначение ролей участникам | Да | Нет | Нет | Нет |
| Создание собственного проекта | Да | Да | Да | Да, после входа |

Проверка членства выполняется в PostgreSQL при каждом запросе. Новая регистрация не предоставляет доступ к существующим проектам. Роль пользователя может различаться между проектами. Владелец сохраняет роль аналитика; изменение собственной роли запрещено. Назначение ролей блокирует строку проекта на время изменения. Неактивная учётная запись теряет доступ при следующем запросе.

Документация операций доступна вошедшему пользователю по адресу `/docs`. Она строится из OpenAPI и содержит ссылку на `/openapi.json`. API использует формы `application/x-www-form-urlencoded`, серверную cookie сессии и поле `csrf`; JSON-тела для POST на этом этапе не используются. Сначала клиент получает `/api/auth/csrf`, затем передаёт полученный токен с формой, сохраняя cookie.

## Хранение и проверка паролей

Пароль приложения содержит 12–128 символов. Он хешируется Argon2id с индивидуальной солью; открытый пароль в БД не сохраняется. Email проверяется по синтаксису и приводится к нижнему регистру. Отправка писем и подтверждение владения адресом пока отсутствуют.

Cookie содержит случайный токен, а таблица `web_sessions` — его SHA-256. При входе, регистрации и выходе токен заменяется. Анонимная сессия действует 30 минут, авторизованная — 8 часов без продления срока при запросах. Удаление сессии после выхода делает прежний токен непригодным. Просроченные записи очищаются при запуске сервера.

Для cookie установлены HttpOnly и SameSite=Lax. Для изменяющих запросов проверяются CSRF-токен и заголовок Origin, когда он присутствует. Разрешены локальные Host; тело формы ограничено 8 КиБ. После пяти неудачных входов для сочетания email/IP вводится блокировка на 15 минут. Регистрация ограничена десятью попытками за 15 минут с одного IP. Счётчики сохраняются в БД. Это ограничение для локального учебного приложения; защита публичного сервиса от распределённых атак требует отдельного развёртывания.

SQL-запросы параметризованы, значения в HTML экранируются. Ответы с пользовательскими данными имеют Cache-Control: no-store. CSP запрещает скрипты и встраивание страниц во фреймы. Сервер работает локально по HTTP, поэтому Secure для cookie выключен. Для размещения вне компьютера нужны HTTPS, Secure-cookie и настройка допустимых адресов. Сброс пароля, подтверждение email и многофакторная аутентификация относятся к дальнейшей разработке.

## Миграции и права PostgreSQL

Прежние миграции и расчётные функции не заменяются. Для веб-модуля используется отдельная цепочка Alembic:

| Назначение | Конфигурация | Таблица версий | Текущая версия |
|---|---|---|---|
| Расчётное ядро | alembic.ini | alembic_version | 0002 |
| Веб-сессии | web_alembic.ini | web_alembic_version | web0001 |

Добавляются две прикладные таблицы: `web_sessions` и `web_auth_attempts`. Всего после этапа — 23 прикладные таблицы и две служебные таблицы Alembic. Перед веб-миграцией проверяется версия ядра 0002. Прежние скрипты регистрации ML и воспроизведения снимков продолжают видеть прежнюю версию схемы.

Для миграции применяется существующая роль `coursework_migrator`. Для веб-сервера требуется отдельная PostgreSQL-роль `coursework_app` с LOGIN, без Superuser, Create DB, Create roles и Bypass RLS. Она не получает CREATE в схеме и не является владельцем прикладных таблиц. `prepare_web --grant-only` выдаёт необходимые права на чтение, ограниченные вставки и обновления, работу с сессиями и нужными последовательностями. Пользовательские роли «Аналитик», «Эксперт» и «ЛПР» хранятся в `project_members`; это отдельное понятие от PostgreSQL-роли сервера. Изоляция проектов обеспечивается серверными проверками, RLS на этом этапе не реализована.

Пароли PostgreSQL запрашиваются через getpass и используются в памяти процесса. В .env и исходные файлы они не записываются. Для веб-сервера вводится пароль coursework_app; пароль учётной записи на странице регистрации задаётся отдельно.

## Установка в существующий проект

Распаковать архив на рабочий стол в `coursework_web_auth`. В терминале VS Code, находясь в `coursework_laptop` и ветке `feature/web-auth`, выполнить:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File "$env:USERPROFILE\Desktop\coursework_web_auth\install_web_auth.ps1"
python -m pip install -r requirements_web.txt
python -m scripts.prepare_web --migrate-only
```

Последняя команда запрашивает пароль coursework_migrator. Затем в pgAdmin под postgres создать Login/Group Role `coursework_app`: задать отдельный пароль, включить Can login и оставить административные привилегии выключенными. Для обычной схемы public PostgreSQL 18 право USAGE доступно PUBLIC. Если настройки отличаются, владелец схемы должен выдать USAGE, а владелец БД — CONNECT к coursework_laptop; приложение проверит наличие необходимых прав.

После создания роли:

```powershell
python -m scripts.prepare_web --grant-only
python -m scripts.run_web
```

Первая команда запрашивает пароль coursework_migrator, вторая — coursework_app. Открыть `http://127.0.0.1:8000/register`, создать собственную учётную запись. Остановка сервера — Ctrl+C. Для повторного запуска достаточно `python -m scripts.run_web`.

## Доступ к ранее загруженному демонстрационному проекту

Демонстрационные пользователи прежнего этапа отключены и не предназначены для входа. После регистрации реальной учётной записи открыть второй терминал в проекте и выполнить, заменив email на свой:

```powershell
python -m scripts.grant_demo_access --email "your-email@example.com"
```

Команда запрашивает пароль coursework_migrator и явно предоставляет выбранной активной учётной записи роль аналитика только в демонстрационном проекте. Повторный запуск не создаёт второго членства. Для технического события в audit_events поле actor_id ссылается на получателя доступа; details прямо указывает происхождение local_administrator_cli и роль БД coursework_migrator, а не вход пользователя через браузер.

После команды обновить страницу проектов. Таблица демонстрации содержит 5 ноутбуков и 25 оценок; пять значений производительности помечены «Прогноз». На странице указано, что эти прогнозы относятся к синтетическому учебному эксперименту.

Назначение доступа обновляет ревизию демонстрационного проекта. Старые результаты расчётов сохраняются и воспроизводятся по историческому снимку, но могут отображаться как устаревшие относительно текущей ревизии. Для нового снимка можно отдельно выполнить прежнюю команду `python -m scripts.calculate_db`. Повторная начальная загрузка демонстрации и ML для открытия веб-интерфейса не требуется.

## Проверки и границы этапа

```powershell
python -m pytest -q
```

Без TEST_DATABASE_URL интеграционные тесты пропускаются явно. Тестовый адрес должен указывать на отдельную тестовую БД: проверки создают временные схемы и роли и удаляют их после завершения; для них нужен тестовый администратор. Веб-сервер не получает эти права.

Регистрация, вход, выход, CSRF, ограничение попыток, срок сессии, отключение пользователя, изоляция проектов, проверка ролей, экранирование HTML, ограничение размера формы и разделение цепочек миграций проверяются автоматически. Проверки в среде подготовки используют PostgreSQL 18 через PGlite и SET LOCAL ROLE; нативное подключение по паролю к пользовательскому PostgreSQL проверяется после установки на Windows.

Этот этап создаёт основу веб-интерфейса. Редактирование и удаление проектов, ввод альтернатив и оценок, веб-запуск MEREC/MARCOS/VIKOR/DEMATEL, обучение ML через браузер, экспорт XLSX и PWA ещё не реализованы. Существующие расчёты доступны прежними командами. Полное выполнение технического задания данным этапом не заявляется.
