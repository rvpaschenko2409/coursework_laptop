# Окончательный выбор ЛПР в веб-приложении

Вариант 27. Этап добавляет фиксацию пользовательского решения после сравнения MARCOS и VIKOR. Разделение ролей соответствует принятому ТЗ: аналитик готовит данные и запускает расчёты, ЛПР рассматривает результаты и фиксирует выбор. Самостоятельное изменение собственной роли по-прежнему запрещено.

## Порядок работы

1. Зарегистрировать отдельного участника для роли ЛПР. Для учебной демонстрации допустима вторая собственная учётная запись с другим email; пароль задаётся в приложении и не включается в проект.
2. Войти как аналитик, открыть проект и блок «Предоставить доступ», указать email зарегистрированного участника и роль «ЛПР». Владелец проекта остаётся аналитиком.
3. После назначения роли заново выполнить расчёт MARCOS и VIKOR: состав участников относится к версии проекта и меняет её. Можно использовать любой из уже реализованных источников весов.
4. Войти как ЛПР, открыть этот проект, затем актуальный результат расчёта и «Окончательный выбор ЛПР».
5. Сравнить ранги и условия VIKOR, самостоятельно выбрать альтернативу, написать обоснование из 20–2000 символов и подтвердить ознакомление с рейтингами и ограничениями.
6. Нажать «Сохранить решение ЛПР». Запись появится в истории; доступны подробности и снимок JSON.

Альтернатива заранее не выбрана. Можно выбрать любой ноутбук из матрицы после бюджетного фильтра. Выбор вне компромиссного набора VIKOR разрешён как самостоятельное решение ЛПР и отмечается предупреждением. Этот выбор не объявляется рекомендацией метода. Оба рейтинга и компромиссный набор остаются доступными.

Аналитик и эксперт видят форму и историю, но не могут сохранять выбор. Архивный проект и устаревший исходный расчёт не допускают нового решения. Сохранение решения само по себе не меняет версию исходных данных.

## Хранение и проверка

Используется существующая таблица `decision_choices`, предусмотренная исходной схемой. Новых таблиц и миграций нет. Запись содержит проект, канонический идентификатор MARCOS из исходной пары, код ноутбука, автора, серверную дату и обоснование. В JSON-снимке хранятся:

- имя и идентификатор автора, роль ЛПР на момент решения, подтверждение ознакомления и ссылка на предыдущее решение;
- полная исходная матрица, оценки, альтернативы, бюджет, параметры и источник весов, происхождение прогнозов;
- записи и результаты обоих методов, выбранная альтернатива с исходными оценками и рангами;
- версия адаптера и SHA-256 контекста.

Снимок включает сведения синтетического эксперимента. Их точность на реальных ноутбуках не подтверждается.

Просмотр подробностей воспроизводит оба рейтинга из сохранённого контекста и сверяет выбранную альтернативу, ранги, веса и основные поля записи. Изменение текущих данных не подменяет старые значения. При другой версии расчётных файлов требуется соответствующая версия проекта из Git. Отпечаток проверяет согласованность и не является электронной подписью или защитой от администратора БД.

Пересмотр создаёт новую запись. Последней считается запись с наибольшим идентификатором в проекте; прежние записи сохраняются. Отдельно отображается, соответствует ли исходный снимок текущей версии проекта. История выдаётся страницами по 20 записей.

## Права и транзакции

Сервер проверяет сессию, CSRF, принадлежность проекту, актуальную роль ЛПР и версию проекта. Перед сохранением блокируется строка проекта и повторно проверяются права. Автор не принимается из пользовательской формы.

Скрытый идентификатор предыдущего решения защищает от сохранения поверх незамеченного нового выбора: при конфликте возвращается HTTP 409. Точный повтор ранее принятого запроса с прежним идентификатором открывает существующую запись. Для MARCOS и VIKOR одной исходной пары используется одинаковый канонический источник. Решение и событие аудита сохраняются одной транзакцией.

`prepare_web_decision_choice` добавляет роли приложения SELECT и INSERT необходимых столбцов таблицы решений и USAGE последовательности. Права UPDATE и DELETE на решения не выдаются. Проверки пользовательских ролей выполняются приложением; разделение участников не реализовано отдельными ролями PostgreSQL для каждого веб-пользователя.

Обоснование нормализуется в Unicode NFC; длина и управляющие символы проверяются на сервере, вывод экранируется. Повторяющиеся и посторонние поля отклоняются. Для формы решения установлен предел тела запроса 32768 байт. Остальные пределы форм сохранены.

## Маршруты

| Назначение | Маршрут |
| --- | --- |
| Форма и сохранение | `/projects/{project_id}/calculations/{result_id}/choice` |
| API сохранения | `/api/projects/{project_id}/calculations/{result_id}/choice` |
| История | `/projects/{project_id}/choices` |
| Подробности | `/projects/{project_id}/choices/{choice_id}` |
| API истории и подробностей | Те же пути с префиксом `/api` |
| Проверка снимка | POST `/api/projects/{project_id}/choices/{choice_id}/replay` |
| JSON | `/projects/{project_id}/choices/{choice_id}/snapshot.json` |

POST требует CSRF. Форма сохранения также передаёт `revision`, `alternative_code`, `reason`, `previous_choice_id`, `acknowledge=yes`. Отсутствующая запись чужого проекта возвращает 404; отсутствие роли ЛПР — 403; конфликт версии — 409; недопустимый выбор — 422.

## Проверка после установки

```powershell
python -m scripts.prepare_web_decision_choice
python -m pytest -q
python -m scripts.run_web
```

Для подготовки прав используется пароль `coursework_migrator`, для сервера — `coursework_app`. До запуска нового сервера следует остановить предыдущий через Ctrl+C.

Обычный pytest без `TEST_DATABASE_URL` пропускает интеграционные проверки БД. Число пропусков нельзя считать подтверждением их выполнения. В автоматической проверке этапа использован изолированный PostgreSQL-совместимый движок PGlite; подключение к пользовательской PostgreSQL на Windows не выполнялось. Точные результаты приведены в `web_decision_choice_checks.json`.

Изменения математического ядра, генератора, моделей, исходных данных и существующих миграций не требуются. Этот этап не завершает все требования курсовой, экспорт в XLSX, JavaScript и PWA.
