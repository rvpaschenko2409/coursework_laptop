# MEREC, MARCOS и VIKOR в веб-интерфейсе

Курсовая работа, вариант 27. Этап от 30.10.2026.

## Реализованные возможности

На странице проекта появилась ссылка на расчёты и историю. Аналитик задаёт параметр v и запускает MEREC, MARCOS и VIKOR одной кнопкой. Эксперт и ЛПР просматривают результаты; запуск для них запрещён сервером. Доступ к чужим проектам, результатам, диаграммам и снимкам проверяется при каждом запросе.

Используются пять критериев исходного варианта. Веса рассчитываются MEREC после бюджетного фильтра. Оба рейтинга строятся на одной матрице и одном наборе весов. MARCOS оценивается по убыванию utility, VIKOR — по возрастанию Q. Для VIKOR выводятся S, R, Q, порог DQ, разрыв с вторым местом, выполнение условий приемлемого преимущества и устойчивости, компромиссный набор. Первый ноутбук по Q не выдаётся автоматически за единственное решение.

Страница результата содержит:

- лидера MARCOS и лидера VIKOR с компромиссным набором;
- таблицу сопоставления рангов и числовых показателей;
- диаграммы весов MEREC и рангов, построенные на Python;
- веса критериев и эффекты их исключения;
- матрицу сохранённого снимка, единицы, направления и источники значений;
- перечень исключённых по бюджету ноутбуков;
- нормированные и взвешенные матрицы, идеал и антиидеал MARCOS, показатели полезности, отклонения VIKOR;
- автора, дату, ревизию проекта, параметры, идентификаторы, версию ядра и отпечаток входов;
- скачивание технического снимка JSON.

Широкие таблицы прокручиваются внутри контейнеров. Диаграмму можно открыть крупнее; точные данные доступны в таблицах. Промежуточные вычисления и технические сведения раскрываются отдельными блоками. История выводится по 20 пар результатов на страницу. Отображаемое время относится к Омску.

## Математическая логика и входные данные

Новые веб-модули используют `load_snapshot`, `compute`, `assert_close` и `replay_result` из существующего decision_store/calculations.py. Формулы MEREC, MARCOS и VIKOR не дублируются. Ни этот файл, ни decision_core не изменяются. Контрольная версия ядра:

`2615dd1e33d27cf817c78c9acfd1c5c39e05de3d8df4a5ab692c3edab6011729`.

Параметр v принимается как конечное число от 0 до 1 включительно. Поддерживаются запятая и точка. Значения NaN, бесконечности, пустая строка и выход за границы отклоняются. Нужны 2–15 альтернатив без повторов, исходные пять критериев с правильными направлениями и положительные конечные оценки.

Цена должна быть известна у каждого ноутбука. Бюджетный фильтр применяется до построения рейтингов. Если после него осталось меньше двух ноутбуков или у допустимой альтернативы не заполнена оценка, результат не сохраняется. Прогнозы ML проверяются по активности модели, значению и снимку признаков. У ручной корректировки прогноза должна быть причина. Пустая производительность в новом проекте без модели остаётся ошибкой готовности матрицы, а не заменяется произвольным баллом.

Контроль для демонстрационного проекта при бюджете 100000 и v=0,5: MARCOS — A4, A2, A5, A3, A1; VIKOR — A2, A3, A5, A4, A1; компромиссный набор — A2, A3, A5. Этот контроль относится к исходным оценкам. Изменение бюджета или оценок закономерно может изменить веса и результаты.

## Авторство, транзакции и повторный запуск

Старый CLI-запуск сохраняет технического автора — владельца проекта. Для веб-запуска добавлен отдельный модуль orchestration, который использует фактического пользователя серверной сессии. Его идентификатор записывается в created_by у весов и обоих результатов, в audit_events и в producer.requested_by сохранённого снимка. Владелец демонстрационного проекта не подставляется вместо вошедшего пользователя.

Перед запуском сервер блокирует строку проекта, заново проверяет роль аналитика и сверяет ревизию с формой. Если данные изменились после её открытия, возвращается 409. Снимок, вычисления и вставки выполняются в одной транзакции. При ошибке откатываются оба результата, набор и значения весов, а также событие аудита. Завершение транзакции происходит до отправки успешного HTTP-ответа.

Для веб-запроса не вызывается целиком прежний `run_calculation`: он требует свежей транзакции REPEATABLE READ и использует владельца проекта как автора. Веб-обработчик уже имеет транзакцию аутентификации; он применяет блокировку проекта и вызывает неизменные функции загрузки и вычисления. Поддерживаемые редакторы и загрузчики синхронизируют изменение данных через ту же строку проекта. Глобальная advisory-блокировка прежнего CLI не захватывается после блокировки проекта, чтобы не менять порядок блокировок.

Отпечаток учитывает полный снимок, ревизию, v, автора запроса и окружение. Детерминированные UUID создаются отдельно для веб-запусков и методов. Повторный запуск одного пользователя с теми же входами открывает существующую пару после проверки её содержимого. Другой автор получает собственные записи; авторство не переписывается. Новый v, изменённые данные или окружение дают новый снимок. Набор MEREC может численно совпадать между запусками, но принадлежит соответствующему сохранённому снимку.

## Исторические результаты

Старая пара CLI и новые веб-пары доступны через одну историю. При чтении пары проверяются оба метода, отпечатки, версия ядра, совпадение снимков и набора весов. Воспроизведение использует старые входы, не текущую таблицу проекта. Проверяются сами сохранённые веса и промежуточный результат MEREC. Различие текущей и сохранённой ревизии показывается как историческое состояние.

Страница не подменяет сохранённые названия, оценки, бюджет или прогнозы новыми. Изменение текущих данных не переписывает старые результаты. Ошибочная или неполная пара не пересоздаётся поверх прежней; сервер сообщает о несовпадении. Для строгого воспроизведения нужна соответствующая версия ядра из Git — изменение математического кода не скрывается.

В API предусмотрен POST `/api/projects/{project_id}/calculations/{result_id}/replay` с CSRF-токеном. Он проверяет воспроизведение, но не создаёт нового расчёта. Диаграммы и скачиваемый снимок также требуют членства в проекте и имеют Cache-Control: no-store. В выгружаемом JSON находятся входы и результаты, без паролей и настроек подключения к PostgreSQL.

## PostgreSQL и установка

Новые таблицы и миграции на этом этапе не требуются. Используются существующие weight_sets, weights, results и audit_events. Версии остаются `alembic_version=0002` и `web_alembic_version=web0002`.

Существующей coursework_app выдаются нужные INSERT и USAGE на две последовательности. Веб-роль не получает UPDATE/DELETE завершённых результатов или весов. Прежний триггер guard_weight_identity блокирует родительский weight_set через SELECT FOR UPDATE. Для такой блокировки PostgreSQL требует UPDATE хотя бы одного столбца; выдано UPDATE(alpha). У используемых здесь наборов MEREC CHECK требует alpha IS NULL. Интерфейс не предоставляет изменение alpha и не меняет сохранённые наборы. Административные права и CREATE в схеме не выдаются. Изоляция проектов обеспечивается сервером; PostgreSQL RLS не заявляется.

Порядок установки:

1. Остановить работающий сервер сочетанием Ctrl+C и дождаться приглашения PowerShell.
2. Распаковать архив на рабочий стол в `coursework_web_calculations`.
3. В терминале coursework_laptop, в чистой ветке `feature/web-calculations`, выполнить:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File "$env:USERPROFILE\Desktop\coursework_web_calculations\install_web_calculations.ps1"
python -m scripts.prepare_web_calculations
```

Ввести пароль coursework_migrator. Команда проверит версии схем и настроит права; повторный запуск допустим. Установщик проверяет исходные контрольные суммы с нормализацией Windows-переносов строк и сохраняет резервные копии четырёх обновляемых файлов рядом с проектом. Данные, модели, математические функции и прежние миграции не заменяются.

Затем:

```powershell
python -m scripts.run_web
```

Ввести пароль coursework_app, войти прежним веб-аккаунтом и открыть демонстрационный проект → «Рассчитать и открыть историю». При v=0,5 нажать «Рассчитать MEREC, MARCOS и VIKOR». Для этого контрольного запуска не нужно добавлять или удалять ноутбуки. Дополнительные библиотеки сверх установленных ранее зависимостей не требуются.

## Проверки и границы этапа

```powershell
python -m pytest -q
```

Без TEST_DATABASE_URL проверки с отдельной тестовой PostgreSQL явно пропускаются. Для подготовки использованы PostgreSQL через PGlite и реальные SQL-права через SET LOCAL ROLE. Проверяются эталонные ранги, границы v, бюджет, неполная матрица, роли, CSRF, чужие идентификаторы, история CLI, повтор без дублей, фактический автор, откат после вставок, историческое воспроизведение, диаграммы, JSON и пагинация. Проверка Chromium охватывает ширины 360, 390, 768, 1366 и 1920 px. Нативные запуск и права Windows/PostgreSQL подтверждаются после установки пользователем.
