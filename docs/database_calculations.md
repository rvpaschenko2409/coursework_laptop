# Расчёты по данным PostgreSQL и исторические снимки

Вариант 27. Версия этапа 1, 30.10.2026. Требуется схема 0002 и заполненная матрица проекта.

## Что выполняет этап

`decision_store/calculations.py` читает исходные сведения из PostgreSQL и вызывает ранее проверенные функции `decision_core`: MEREC для весов, MARCOS и VIKOR для ранжирования. Командный интерфейс — `python -m scripts.calculate_db`. При расчёте не читаются CSV, не загружаются joblib и не выполняется обучение. Используются сохранённые в БД оценки и прогнозы с происхождением. Контрольные CSV используются только тестами.

Математические функции и их формулы не заменяются. На этом этапе поддержан исходный состав пяти критериев: price_rub и mass_kg минимизируются; performance_score, battery_hours и warranty_months максимизируются. Для произвольных 2–10 критериев из целевого ТЗ ещё требуется параметризация ядра; текущий этап не объявляет эту функцию завершённой. Число альтернатив — от 2 до 15.

## Проверка входных данных

Для каждой альтернативы нужна цена: без неё нельзя проверить бюджет. Бюджет применяется до формирования расчётной матрицы. В снимке сохраняются все альтернативы, список допущенных и коды исключённых по цене. После фильтра должно остаться не меньше двух альтернатив; у допущенных должны быть заполнены все пять оценок. Неизвестные значения не заменяются нулями.

Проверяются конечность и положительность, отсутствие повторов, состав критериев, направления, ссылки прогнозов и совпадение оценки источника ML с исходным прогнозом. Изменение входных характеристик ноутбука при прежнем прогнозе отклоняется как устаревший прогноз. Для источника ML модель должна быть активной. Ручная корректировка может отличаться от исходного прогноза; её причина и связь с прежним прогнозом остаются в снимке и истории оценок.

Проект со статусом archived не рассчитывается. Параметр VIKOR v — конечное число от 0 до 1, по умолчанию 0,5. В этом этапе веса всегда рассчитываются MEREC. Ручные, DEMATEL и комбинированные веса в данном запуске не подменяются им неявно; соответствующие режимы будут подключаться отдельным развитием сервиса.

## Сохранённые сведения

В одной транзакции создаются:

- одна запись weight_sets метода merec и пять строк weights;
- две завершённые записи results: marcos и vikor;
- одно событие audit_events с идентификаторами результатов, набора весов и ролью БД, запустившей CLI.

В weight_sets.input_snapshot сохраняются исходный снимок и расчёт MEREC: специальное нормирование, оценки S, оценки без каждого критерия, эффекты исключения и веса. В results.output находятся рейтинги и промежуточные таблицы: у MARCOS — нормированная/взвешенная матрицы, идеал, антиидеал и их суммы, S/K/f/utility; у VIKOR — расстояния, взвешенные расстояния, S/R/Q, условия и компромиссный набор.

Оба результата содержат одинаковый самодостаточный input_snapshot: цель, бюджет и ревизию проекта, критерии/единицы/направления, альтернативы и характеристики, оценки с источниками и причинами коррекций, использованные predictions, версии моделей и метрики, сведения о наборе данных и его SHA-256, порядок строк и столбцов матрицы, параметры и ограничения. Файлы моделей и все 2000 обучающих строк в снимок не копируются: для повторного MCDA-расчёта достаточно сохранённых прогнозов; для обучения нужны исходные версии артефактов.

Числовые веса в таблице weights хранятся с точностью NUMERIC(18,15). Для строгого пересчёта используется полный сохранённый расчёт MEREC в JSONB, а не округлённая таблица. Ограничение БД проверяет сумму весов в конце транзакции.

## Версия ядра и повторный запуск

Хеш исходных файлов расчётного ядра и сервиса хранится как core_version; при хешировании переводы строк нормализуются, чтобы LF/CRLF не создавали искусственную смену версии. Снимок также фиксирует версии Python, NumPy и pandas. Контрольная сумма всего снимка определяет UUID пары и отдельные request_key для MARCOS/VIKOR.

Повторный запуск при тех же входах и параметрах проверяет существующие выходы и веса и возвращает прежние идентификаторы без новых строк. Изменение оценки, бюджета, цели, признаков, параметра v или версии сервиса создаёт другой снимок и новые результаты. При изменении v пара создаётся целиком, хотя на математический результат MARCOS сам v не влияет.

Старые завершённые results не обновляются — это запрещено триггером схемы. Таблицы предметных данных, прогнозы и модели расчёт не изменяет. Удаление всего проекта по существующим правилам схемы каскадно удаляет и его историю; такое действие требует отдельного пользовательского сценария и не выполняется этим CLI.

## Воспроизведение результата

```powershell
python -m scripts.calculate_db --replay ID_РЕЗУЛЬТАТА
```

Вместо ID_РЕЗУЛЬТАТА указывается число из result_ids последнего вывода. Воспроизведение берёт матрицу и происхождение из исторического снимка, а не из текущих scores. Проверяются контрольная сумма, ревизия снимка и совпадение сохранённого выхода с пересчётом; числовой допуск — 1e-10. Показатель is_stale сравнивает сохранённую ревизию проекта с текущей. Устаревший по ревизии результат может корректно воспроизводиться и остаётся историческим, а не текущим решением.

Если хеш ядра изменён, строгая проверка останавливается. Для воспроизведения нужен соответствующий исходный код из Git. Никакой код из JSONB автоматически не исполняется. Текущие значения цели, цены и т.п. не подставляются вместо исторических.

## Транзакции и ограничения реализации

Сервис запускается в новой транзакции REPEATABLE READ, использует общую с начальными загрузчиками advisory-блокировку и блокировку строки проекта. Чтение метаданных и оценок относится к одному согласованному состоянию БД. CLI повторяет транзакцию до трёх раз при конфликте сериализации/взаимной блокировке или конкурентной вставке того же request_key. Нагрузочное испытание параллельных клиентов на установленной PostgreSQL ещё не проводилось.

Если сохранение VIKOR не удалось после вставки MARCOS, откатываются оба результата и набор весов. Сообщение об успехе печатается только после COMMIT. Неуспешная попытка этого синхронного CLI не оставляет отдельной записи failed; журнал фоновых задач и отображение ошибок в приложении ещё предстоят.

Доступ сейчас осуществляется через coursework_migrator для проверки этапа. Actor_id — учебный владелец проекта, а роль БД отдельно отмечается в аудите; это не означает готовую авторизацию приложения. Перед подключением веб-интерфейса нужны серверные проверки прав и отдельная роль БД с ограниченными привилегиями. Формирование интерфейса, экспорт, произвольные критерии, анализ чувствительности, PWA и финальные испытания остаются последующими этапами.

## Запуск демонстрации

```powershell
python -m scripts.calculate_db
```

По умолчанию: проект 1, v=0,5, база coursework_laptop, localhost:5432. Пароль coursework_migrator вводится скрыто и не сохраняется в файлах. Для другого проекта есть --project-id, для параметра VIKOR — --v, для порта — --port.

При исходном проекте ожидаются: лидер MARCOS A4, лидер по Q VIKOR A2, компромиссный набор A2/A3/A5. Выбор по VIKOR не сводится к автоматическому утверждению одного ноутбука; окончательное решение принимает ЛПР. Показатели производительности остаются синтетическими.

Повтор той же команды должен дать created=false и прежние result_ids. SELECT для просмотра рейтингов и весов: `sql/004_verify_calculations.sql`. Новая миграция и установка библиотек не нужны.

## Проверки и источники

Автономные тесты сравнивают веса и рейтинги с прежними контрольными CSV, проверяют бюджет, неполные оценки, устаревшие прогнозы, направления, v и повреждение матрицы снимка. Интеграционная проверка использует реальные psycopg/SQL, создаёт отдельную случайную схему, загружает demo/ML, проверяет повтор, изменение цены, воспроизведение старого снимка и транзакционный откат при искусственной ошибке второй вставки. Во время расчёта чтение CSV принудительно запрещено тестом.

Протокол — `docs/database_calculations_checks.json`. Среда проверки: PostgreSQL в WebAssembly (PGlite) через TCP, не компьютер студента. Без TEST_DATABASE_URL четыре интеграционных теста всего проекта пропускаются. Измерение НФТ-01 на целевом стенде ещё не выполнено.
